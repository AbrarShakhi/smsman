SMS Man — Bugs, Missing Features & Improvements

A full read-through of the Android SMS/MMS client in this repository, against the stated goal of a fully-featured, production-level, Play-Store-submittable app.

Generated 2026-06-01 · package com.abrarshakhi.smsman · Kotlin 2.3.10 · Compose · Hilt · Room · Nav3 · ~90 Kotlin files reviewed. Companion document: Code Review & architecture walkthrough.

Executive summary

The project is well-architected and surprisingly complete in surface area — clean layering (domain / data / framework / ui), MVI screens, Nav3, dynamic theming, onboarding with the default-SMS-app role, search, scheduling and a settings surface are all present and largely wired correctly. As a UI/architecture skeleton it is genuinely good.

However, it is not production-ready. Several core messaging guarantees are broken or unimplemented: the sent/delivered status that the UI draws is decoded with the wrong number scheme, blocking does not actually block, the multi-recipient compose UI silently drops everyone but the first recipient, MMS is entirely a stub, notifications ignore mute and never show conversation history, and tapping a notification while the app is open doesn't open the thread. On top of that there are zero real tests, no string localization, a destructive DB migration left in, and a couple of Google Play policy risks (restricted SMS permissions + an unused USE_EXACT_ALARM).

① Critical & high-severity bugsThese break a guarantee a messaging app must keep.

CRITICAL B1 — Sent / delivered status uses two incompatible number schemes; “Delivered” never shows #status-mapping

domain/model/Message.kt:43–54 data/repository/MessageRepositoryImpl.kt:94 framework/receiver/SmsSentStatusReceiver.kt:35–44 framework/receiver/SmsDeliveredStatusReceiver.kt:36–46 ui/screens/chat/components/MessageBubble.kt:154–168

The status column is written with Android’s Telephony.Sms.STATUS_* constants (NONE=-1, COMPLETE=0, PENDING=32, FAILED=64) but read back through the app’s own MessageStatus.fromRaw(), whose values are None=-1, Sending=0, Sent=1, Delivered=2, Read=3, Failed=64. The two scales only line up by accident at -1 and 64:

// Receiver writes Telephony STATUS_COMPLETE = 0 …
messageDao.updateStatus(messageId, Telephony.Sms.STATUS_COMPLETE /* 0 */, errorCode)
// … but the bubble decodes 0 as MessageStatus.Sending — not delivered/sent.
0  -> Sending     // should mean COMPLETE/Delivered
32 -> (no match) -> None
2,3 (Delivered, Read) // are NEVER written by any code path

Because MessageStatus.Delivered/Read are never stored, the “double-check / delivered” branch in statusIcon() is unreachable. Delivery reports are requested, received and recorded — and then rendered as a perpetual Sending clock or a single check.

Impact The single most visible promise of an SMS app — “Sent / Delivered” ticks — is wrong. Delivery receipts (a headline setting) have no visible effect.

Secondary defect in the same area: SmsSentStatusReceiver updates the Telephony row type via smsSender.updateRowType() but never updates the Room type; the row only self-corrects later when the ContentObserver re-imports. And the delivery receiver writes status only to Room, not to Telephony, so the next import can clobber it.

Fix Pick one numbering scheme. Either (a) store domain MessageStatus.raw everywhere and translate Telephony.Sms.STATUS_* → MessageStatus in the receivers, or (b) keep raw Telephony status in the DB and translate at render time. Map COMPLETE→Delivered, PENDING→Sending, FAILED→Failed. Update the Room type in the sent receiver too, and write delivery status to both stores (or stop double-sourcing status).

CRITICAL B2 — “Block” doesn’t block; two disconnected block stores + normalization mismatch #blocking

ui/screens/chat/ChatViewModel.kt:194–201 data/repository/ConversationRepositoryImpl.kt:43–44 data/telephony/SmsInboundHandler.kt:56, 156 data/repository/BlockedNumberRepositoryImpl.kt:25–33 ui/screens/blocked/BlockedNumbersScreen.kt:134

There are two unrelated notions of “blocked” that never talk to each other:

  • Chat → “Block sender” calls conversationRepository.setBlocked(threadId,true), which only flips the conversations.blocked column (moves the thread to the “Blocked” tab).
  • Settings → Blocked numbers writes the separate blocked_numbers table.
  • Inbound filtering (SmsInboundHandler) consults only blocked_numbers.

So blocking a sender from the conversation (the obvious path) does not stop their messages — they keep arriving and keep posting notifications. And even the Settings path is unreliable: the dialog stores the number verbatim (e.g. +8801…), but the inbound check does isBlocked(normalize(sender)) where normalize strips everything but digits. An exact-string DAO match between "+8801712345678" (stored) and "8801712345678" (normalized) fails.

Impact A core safety feature is effectively non-functional. Users will believe they’ve blocked a harasser/spammer and keep receiving messages and notifications.
Fix Unify on one mechanism. Normalize numbers to E.164 once (see B-improve “phone normalization”) and store the normalized form. Have setBlocked(thread) also insert every recipient address into blocked_numbers (and unblock symmetrically), and make the inbound check normalize identically. Optionally integrate the system BlockedNumberContract (available to the default SMS app) so blocks are shared OS-wide.

CRITICAL B3 — Multi-recipient compose silently drops all but the first recipient #multi-recipient

ui/screens/compose/ComposeNewViewModel.kt:103–118 data/repository/MessageRepositoryImpl.kt:51

The New-message screen lets the user add any number of recipient chips and the ViewModel passes them all to SendRequest(recipients = …). But the repository does:

val recipient = request.recipients.first()  // everyone else is dropped, no warning

The message is sent to the first recipient only; the others receive nothing and the user is told it succeeded. Group/MMS sending (the comment says “M4”) was never implemented, yet the UI exposes the entry point.

Impact Silent message loss — the worst kind of messaging bug. A user composing to 5 people reaches 1.
Fix Short term: restrict the compose UI to a single recipient (or loop and send an individual SMS per recipient and create a thread each). Long term: implement real group messaging via MMS. Never accept N recipients and silently use 1.

HIGH B4 — Tapping a notification while the app is alive doesn’t open the thread #deeplink-newintent

MainActivity.kt:31, 37, 43–55

The activity is launchMode="singleTop". The deep link (smsman://thread/<id>) is parsed once in onCreate into a local coldDeepLink captured by the composition. When the app is already running, the OS calls onNewIntent(), which only does setIntent(intent) — nothing re-parses the link or pushes a ChatRoute:

override fun onNewIntent(intent: Intent) {
    super.onNewIntent(intent)
    setIntent(intent)        // captured but never acted on → no navigation
}
Impact The primary reason to tap a message notification — jump to that conversation — fails whenever the app is in memory (the common case). Secondary: a cold deep-link starts the back-stack at ChatRoute only, so Back exits the app instead of going to the conversation list.
Fix Expose the current intent as state (e.g. collect Activity new-intent into a StateFlow) and in a LaunchedEffect push ChatRoute(threadId) onto the back stack. Seed the cold back-stack as [ConversationListRoute, ChatRoute(id)] so Back works.

HIGH B5 — ACTION_SEND / ACTION_SENDTO are advertised but never handled #send-intents

AndroidManifest.xml:72–90 MainActivity.kt:48–55 (parses only the smsman scheme)

The manifest registers MainActivity for SENDTO (sms:/smsto:/mms:/mmsto:) and SEND (text/image/video share). These are the standard “open in messenger” and “share to” entry points — and being a complete SMS app means handling them. But parseDeepLink() returns null for anything that isn’t smsman://thread, so the app just opens to the conversation list and discards the recipient/shared content.

Impact “Message” links from the dialer/contacts and “Share → SMS Man” from the gallery do nothing useful. For a default SMS app this is expected, advertised behaviour that’s missing.
Fix Parse ACTION_SENDTO/VIEW with sms: schemes → pre-fill ComposeNewRoute(recipient); parse ACTION_SEND EXTRA_TEXT/EXTRA_STREAM → compose with body/attachment.

HIGH B6 — Notification “unread history” loader is a no-op; MessagingStyle only ever shows one message #notif-history

data/telephony/SmsInboundHandler.kt:131–147

The code intends to load the thread’s unread messages so the notification re-renders the conversation. It actually discards the flow:

val unread = messageDao.observeByThread(threadId)
    .let { /* one-shot read */ }   // returns Unit; nothing is read
val unreadList = listOf(UnreadMessage(sysId, body, timestamp))  // only the newest

MessagingStyle is then built from a single-element list, so multiple unread messages in a thread never stack the way the coordinator’s doc comment promises (“re-renders the whole conversation each time”).

Impact Notifications lose prior unread context; every new message replaces rather than appends, defeating the MessagingStyle design.
Fix Actually read recent unread rows: messageDao.observeByThread(threadId).first() (it’s already a suspend context), filter to inbound & unread, map to UnreadMessage, cap at ~6, pass the list.

HIGH B7 — Mute is recorded but ignored; muted threads still post high-priority notifications #mute

data/telephony/SmsInboundHandler.kt:141–147 framework/notification/MessageNotificationCoordinator.kt:48–100

Both the per-conversation overflow “Mute” and the multi-select “Mute” set conversations.muted. But the inbound path posts a notification unconditionally — it never reads existing?.muted, and postIncoming() has no mute parameter and always uses the high-importance MESSAGES_DEFAULT channel.

Impact Mute appears to work (toast says “Muted”) but does nothing. Also: the dedicated MESSAGES_BLOCKED / low-priority channels exist but are never used.
Fix Pass the muted flag into postIncoming; if muted, either skip the notification or post silently (setSilent(true) / a low-importance channel) with no vibration/sound.

HIGH B8 — “Default SIM for sending” setting has no effect #default-sim

ui/screens/settings/SettingsScreen.kt:125–135 domain/model/AppSettings.kt:10 data/repository/MessageRepositoryImpl.kt:43–111 (send)

On dual-SIM devices the user can pick a default subscription. It is persisted to DataStore and read back into AppSettings — but no send path ever consults it. ChatViewModel.send uses conv.subscriptionId ?: -1; ComposeNewViewModel.send hard-codes -1 (SmsManager default). The setting is wired to the UI chip only.

Impact Dual-SIM users who choose a sending SIM are silently ignored; outbound goes on the system default SIM.
Fix When the request’s subscriptionId is -1, fall back to settings.defaultSubscriptionId before handing off to SmsSender.

CRITICAL B9 — Destructive Room migration left enabled (data-loss landmine for v1.1) #db-migration

di/DatabaseModule.kt:27–32

The DB is built with fallbackToDestructiveMigration(dropAllTables = true). The in-code comment even says “Replace with real Migration() steps before public release.” The schema is at version = 1 now, so it’s harmless today — but the first time you bump the schema after shipping, every user’s pins, archives, drafts, blocked flags, mutes and scheduled-message rows are silently wiped.

Impact Guaranteed local-data loss on the first post-launch schema change. A release blocker for a “submittable” app.
Fix Add explicit Migration objects (you already export schemas to app/schemas/ and depend on room-testing, so migration tests are easy). Remove destructive fallback before the first store release.

② Medium-severity bugs

MEDIUM B10 — Replying from a notification doesn’t mark the thread read

framework/receiver/NotificationReplyReceiver.kt:42–56

After a direct-reply succeeds the receiver cancels the notification but never calls markThreadRead, so the conversation’s unreadCount stays elevated and the thread still shows an unread badge after you’ve answered it. (Mark-read and swipe-to-dismiss do call it; reply is the outlier.)

Fix Call messageRepository.markThreadRead(threadId) on a successful reply.

MEDIUM B11 — Scheduled send uses inexact WorkManager, not AlarmManager — and requests exact-alarm permissions it never uses

data/repository/ScheduledMessageRepositoryImpl.kt:40–66 AndroidManifest.xml:27–28

Scheduling enqueues a OneTimeWorkRequest with setInitialDelay. WorkManager is explicitly not exact — under Doze/standby a “send at 9:00” can slip by many minutes to hours. Meanwhile the manifest declares SCHEDULE_EXACT_ALARM + USE_EXACT_ALARM which are never used (no AlarmManager anywhere). See also B-PS3 — USE_EXACT_ALARM is a Play-restricted permission.

Fix For time-critical sends use AlarmManager.setExactAndAllowWhileIdle → a receiver that enqueues the worker, or drop the exact-alarm permissions and set user expectations (“approximately”). Don’t request restricted permissions you don’t use.

MEDIUM B12 — RespondViaMessageService never sends the canned reply

framework/service/RespondViaMessageService.kt:21–25

The component exists (required for the role) but on ACTION_RESPOND_VIA_MESSAGE it just logs and stopSelf(). When a user picks “reply with message” while declining a call, the system hands the text in the intent and expects the default app to send it — here it’s dropped.

Fix Extract recipients from the intent data and the body from EXTRA_TEXT / Intent.EXTRA_TEXT, then call MessageRepository.send.

MEDIUM B13 — External deletions/edits in the Telephony provider never propagate to Room

data/telephony/TelephonyImporter.kt:38–48

The importer only upserts the most-recent 1000 rows; it never deletes Room rows that disappeared from Telephony. If another SMS app (or the system) deletes a message, the ContentObserver fires but the row lingers in Room and keeps showing in SMS Man. Over time Room also drifts (rows imported earlier are never pruned).

Fix After import, reconcile: delete Room messages whose ids are no longer present in the imported window (bounded by the same date range), or diff against the provider.

MEDIUM B14 — Search-in-conversation results don’t navigate anywhere

ui/nav/AppNavHost.kt:83–88 ui/screens/search/SearchInThreadScreen.kt:61 (onResultClick defaults to {})

The in-thread search builds tappable result rows, but the nav graph wires only onBack; onResultClick keeps its no-op default. Tapping a match does nothing — you can’t jump to the message.

Fix Wire onResultClick to pop back to the chat and scroll the LazyColumn to that message id (requires exposing a “scroll to id” signal to ChatScreen).

MEDIUM B15 — Backup/restore writes only Room, bypassing Telephony, with no transaction or FK safety

data/repository/BackupRepositoryImpl.kt:39–48

Import upserts conversations then messages with their original ids. Issues: (1) restored messages are not written back to the Telephony provider, so they’re invisible to other SMS apps and the next sync can diverge/overwrite them; (2) no @Transaction — a mid-import failure leaves a partial DB; (3) a message referencing a missing thread id violates the FK; (4) importing onto a populated device can overwrite existing rows by id collision. Exported JSON is also plaintext message content.

Fix Wrap import in a Room transaction; validate/ensure parent conversations exist; decide whether restore should re-insert into Telephony; consider id remapping; warn the user that the export is unencrypted.

MEDIUM B16 — Navigation back-stack is lost on process death

ui/nav/AppNavHost.kt:21

val backStack = remember { mutableStateListOf(startKey) } uses remember, not rememberSaveable or a ViewModel. After the OS kills and restores the process (very common on Android), the user is dropped back to the start destination, losing their place in a deep chat/settings flow.

Fix Hold the back stack in a ViewModel or make the route keys @Serializable/Parcelable and use a saveable back stack (Nav3 supports saveable state holders).

MEDIUM B17 — ScheduledSendWorker marks failed and returns retry(); duplicate-send risk

framework/worker/ScheduledSendWorker.kt:40–45

On failure it both calls markFailed() (status → Failed, drops out of the pending list) and returns Result.retry(). WorkManager will re-run with the same id and try to send again; the row is no longer “pending” but the worker re-fetches it by id regardless. There’s also no idempotency guard, so a send that dispatched to SmsManager but then threw could be re-sent.

Fix Choose one: either Result.retry() with a bounded attempt count and without marking failed until attempts are exhausted, or Result.failure() after marking failed. Guard against re-send (check status at the top of doWork).

MEDIUM B18 — AMOLED/“Black” theme is silently ignored when dynamic color is on (the default)

ui/theme/Theme.kt:91–99

Selection order checks canDynamic before themeMode == Black. Since dynamicColor defaults to true on Android 12+, choosing “AMOLED” yields the dynamic dark scheme (grey surfaces), never the true-black BlackColorScheme, unless the user first turns off dynamic color. The two settings interact in a non-obvious way.

Fix Let Black force black surfaces even under dynamic color (apply .copy(background/surface = Black) to the dynamic dark scheme), or disable the AMOLED chip while dynamic color is on with an explanation.

MEDIUM B19 — allowBackup="true" with default (empty) backup rules backs the message DB to the cloud

AndroidManifest.xml:50–52 res/xml/backup_rules.xml, res/xml/data_extraction_rules.xml (both still template stubs)

Auto Backup is enabled and unconfigured, so the Room database (message bodies) and DataStore get backed up to Google Drive and transferred device-to-device. Beyond the privacy consideration for an SMS app, a restore can repopulate Room with messages that no longer match the new device’s Telephony provider, causing duplicates/ghosts.

Fix Decide deliberately: either exclude the message DB from backup (the Telephony provider is the source of truth anyway) or keep it and reconcile on first launch. Fill in the extraction/backup rules rather than shipping the templates.

MEDIUM B20 — Recipient matching uses substring contains(), risking wrong-thread merges

data/telephony/SmsInboundHandler.kt:97 data/repository/MessageRepositoryImpl.kt:71

existing?.recipientAddresses?.takeIf { it.contains(sender) } is a raw substring test. "+1234" “contains” "234"; a short address can false-match a longer stored one. It’s a soft heuristic on a comma-joined string rather than a real address comparison.

Fix Split on commas and compare normalized addresses for equality, don’t substring-match.

③ Low-severity / polish bugs

LOW B21 — LIKE search doesn’t escape % / _ wildcards

data/db/dao/MessageDao.kt:39–56

Queries like body LIKE '%' || :query || '%' treat a user-typed % or _ as a wildcard, so searching for literally “50%” matches too much. Not a crash, but incorrect results.

Fix Escape wildcards and add ESCAPE '\\', or use an FTS table for proper search.

LOW B22 — Scheduling allows times in the past (sends immediately, no validation)

ui/screens/chat/ChatScreen.kt:180–234

The date/time picker doesn’t prevent selecting a past instant; the delay is coerced to 0 and the message goes out at once with no warning.

Fix Validate scheduledAt > now and disable/explain the confirm button otherwise.

LOW B23 — Default-SMS-app banner only refreshes after the in-app role prompt

ui/screens/conversations/ConversationListScreen.kt:80–92 ui/screens/conversations/ConversationListViewModel.kt:67–69

onResume() is called only from the role-request launcher callback, not on real Android ON_RESUME. If the user changes the default SMS app via system Settings and returns, the “Not default” banner can be stale.

Fix Re-check on Lifecycle.Event.ON_RESUME (e.g. LifecycleEventEffect).

LOW B24 — SimRepositoryImpl reads the deprecated SubscriptionInfo.number (usually null)

framework/SimRepositoryImpl.kt:31

info.number is deprecated and returns empty on most carriers/Android versions without extra permission, so the SIM’s phone number rarely shows.

Fix Use SubscriptionManager.getPhoneNumber(subId) (API 33+) with a graceful fallback.

LOW B25 — Inbound contact resolution can block the 10s goAsync() window

data/telephony/SmsInboundHandler.kt:141

The receiver resolves the contact synchronously inside the goAsync window. Usually fast, but a slow ContactsContract query plus DB writes risk the 10-second broadcast limit on a cold provider.

Fix Post the notification with the raw address first, resolve the contact lazily, then update the notification.

LOW B26 — Dead/duplicated code

ui/screens/Placeholders.kt (empty “can be deleted” file) data/telephony/TelephonySyncCoordinator.kt:100 & ui/screens/conversations/ConversationListViewModel.kt:163 (identical private collect() helpers) ui/screens/search/*Screen.kt (two copies of buildHighlighted)

Minor smells: an empty placeholder file, a hand-rolled Flow.collect() shim duplicated in two files (just use collect {} / collect { … } directly), and a duplicated highlight helper.

LOW B27 — Notification action icons reuse the app icon; error errorCode never surfaced

framework/notification/MessageNotificationCoordinator.kt:123,142,160 framework/receiver/SmsSentStatusReceiver.kt:33–35

Reply/Mark-read/Delete actions all use R.drawable.ic_notification instead of distinct glyphs. And a failed send stores a resultCode as errorCode that the UI never reads/explains (no “tap to retry / why it failed”).

LOW B28 — README & Settings text are stale/contradictory

README.md (Status table + “Known limitations”) ui/screens/settings/SettingsScreen.kt:152,161 (“Export to XML”, “M5f”, “M5c” labels)

README says backup/restore is “deferred / none” and scheduled-from-chat “isn’t surfaced yet,” but both are implemented in code. Settings says “Export to XML” though the code exports JSON, and surfaces internal milestone codes (“M5f”, “M5c”) to end users.

Fix Reconcile docs with reality; remove milestone codes from user-facing copy.

④ Missing features (vs. “fully-featured” SMS/MMS app)Gaps between the stated ambition and what’s implemented.

MAJOR M1 — MMS is entirely a stub (receive, send, attachments)

framework/receiver/MmsWapPushReceiver.kt:15–20 (logs the PDU size, decodes nothing) data/db/dao/AttachmentDao.kt & AttachmentEntity (declared but never read/written anywhere) data/db/mapper/Mappers.kt:46 (attachments = emptyList() always) data/telephony/TelephonyImporter.kt (SMS only — no content://mms join)

The app presents itself as an SMS/MMS client (manifest WAP-push receiver, RECEIVE_MMS, Coil “for MMS attachments”, an MMS bubble label, an Attachment model + DAO). In reality: incoming MMS is logged and dropped; no PDU decode, no MMSC download, no attachment storage; the entire AttachmentDao is dead code; outgoing MMS/attachment send isn’t built (the attach button is a stub). Message bodies for MMS just render the literal text “MMS”.

Impact No photos, no group messaging, no subject lines — a large part of “fully featured.”

FEATURE M2 — No attachment / image sending (the paperclip & emoji buttons are no-ops)

ui/screens/chat/components/UserInput.kt:57–59, 99–104

Attach and emoji IconButtons have empty onClick bodies (commented “M4”/“M5+”). Sending images is a baseline expectation for a modern messenger.

FEATURE M3 — No localization / RTL string coverage

res/values/strings.xml (only app_name)

30+ user-facing strings are hard-coded in Kotlin; stringResource is used 0 times. The app can’t be translated and won’t pass a basic i18n bar. (supportsRtl is set, but the literal strings aren’t externalized.)

FEATURE M4 — Other expected-but-absent niceties

No tablet/foldable list-detail layout (the material3-adaptive deps are pulled in but unused); no message reactions/forwarding; no per-conversation custom notification sound; no “mark as spam”; no contact/vCard rendering despite Attachment.isContact; no scroll-to-searched-message; no resend-failed action; no empty-DB “import existing messages” progress UI; no widget/quick-tile.

QUALITY M5 — Effectively no automated tests

app/src/test/.../ExampleUnitTest.kt (asserts 2+2=4) app/src/androidTest/.../ExampleInstrumentedTest.kt (package-name check)

All test infrastructure is wired (JUnit, MockK, Turbine, coroutines-test, room-testing, work-testing) but there are no real tests. For a “production” app, the status-mapping, blocking, grouping (ChatGrouping), importer, and send/receive flows urgently need unit coverage — most of the Critical bugs above would have been caught by a handful of tests.

QUALITY M6 — No crash/error reporting, logging strategy, or analytics

Errors are swallowed with Log.e; there’s no Crashlytics/Sentry, no user-visible failure surfacing for background paths (failed imports, failed scheduled sends beyond a list status). Fine for a prototype, expected for production.

FEATURE M7 — Phone-number normalization is a placeholder

data/telephony/SmsInboundHandler.kt:152–156 (digits-only, comment defers “E.164 … in M1.4”)

There’s no real E.164 normalization (no libphonenumber). This is the root cause behind B2 (blocking) and contributes to contact-match and thread-merge inconsistencies.

⑤ Google Play readiness checklist

  • Default-SMS-app role & restricted SMS permissions (READ_SMS, SEND_SMS, RECEIVE_SMS/MMS/WAP_PUSH): correctly gated behind being the default app, but they require a Permissions Declaration in Play Console and an approved use case. Plan for review friction. (AndroidManifest.xml:10–14)
  • USE_EXACT_ALARM is a policy risk — Play restricts it to alarm/clock/calendar apps; an SMS app may be rejected. It’s also unused here. Remove it. (AndroidManifest.xml:28) — see B11.
  • Destructive DB migration will wipe user metadata on the first schema bump — fix before release. (B9)
  • No privacy policy / data-safety mapping evident; an SMS app must complete the Data Safety form (reads SMS & contacts) and host a privacy policy.
  • Auto Backup of message content is on with unconfigured rules (B19) — review against the Data Safety declaration.
  • Core function correctness: sent/delivered status (B1), blocking (B2), multi-recipient (B3) and notification tap (B4) are broken — Play’s SMS policy and basic QA expect these to work.
  • Release build hygiene: R8 minify + resource shrink enabled, sensible ProGuard keep rules, no debuggable leak, versionCode/versionName set. (app/build.gradle.kts:29–38)
  • Target SDK is current (36) with min SDK 30 — meets Play target-API requirements.
  • No tests / CI (M5) — not a Play gate, but a production-readiness gap.
  • No localization (M3) — limits reach; not a hard gate.
  • Accessibility: most icons have contentDescription (good), but custom BasicTextField input bars and the avatar/initials need a TalkBack pass.
