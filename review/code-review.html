SMS Man — Code Review & “How Everything Works”

An architecture walkthrough and clean-code assessment of the Android SMS/MMS client in this repo.

Companion to the Bugs & Improvements report (referenced as B# / M# below). 2026-06-01 · com.abrarshakhi.smsman.

Is this clean code?

Yes — structurally. This is clean, idiomatic, modern Android. The layering is disciplined, the Kotlin is fluent, the Compose is current, and the DI/threading conventions are consistent. As a codebase to read and extend it is well above average. But “clean” is not the same as “correct” or “done.” Underneath the tidy surface, several core flows are wired to the wrong values or are stubs, and there are no tests to catch it. So: clean architecture, immature correctness.

What “clean” looks like here, concretely:

  • Strict dependency direction — domain has zero Android imports; ui talks to interfaces, never to *Impl; framework isolates platform glue. The package boundaries are real, not aspirational.
  • Consistent MVI — every screen is State + Intent + Effect + onIntent(), with StateFlow/SharedFlow. Once you read one ViewModel you can read them all.
  • Idiomatic Kotlin/coroutines — withContext(io) at the data boundary, flatMapLatest for thread switching, debounce for drafts/search, injected dispatchers for testability.
  • Good comments where it matters — the tricky bits (reverse-layout day dividers, PendingIntent request-code packing, multipart status caveats) are explained, not just written.

And where it falls short of clean:

  • Correctness defects hidden behind tidy code (the status enum collision, B1; blocking split across two stores, B2).
  • No tests at all (M5) — so “clean” is unverified; refactors are unguarded.
  • A few dead/stub artifacts shipped as if real (AttachmentDao, MMS receiver, RespondViaMessageService, Placeholders.kt).
  • Documentation (README, settings labels) has drifted from the code.

How everything works — the big picture

SMS Man is a default-SMS-app client. The Android Telephony provider (content://sms, content://mms-sms) is treated as the system source of truth; the app keeps a local Room mirror for fast Compose queries plus its own metadata (pin, archive, block, mute, draft, scheduled). The UI reads Room; writes go to Telephony first (so other apps stay consistent), then Room.

┌──────────────────────────────────────────────────────────┐ │ UI (Compose, MVI) │ │ Screens ⇄ ViewModels ⇄ domain Repository interfaces │ └───────────────┬──────────────────────────────┬────────────┘ │ StateFlow/Effects │ suspend calls ┌───────────────▼──────────────────────────────▼────────────┐ │ domain/ (pure Kotlin) │ │ models (Message, Conversation, …) + 9 interfaces │ └───────────────┬──────────────────────────────┬────────────┘ Hilt @Binds (di/RepositoryModule) ┌───────────────▼──────────────────────────────▼────────────┐ │ data/ (impls) │ │ *RepositoryImpl Room DAOs/Entities DataStore │ │ telephony/ (importer, inbound, observer) │ └───────┬───────────────────┬──────────────────┬─────────────┘ │ Room │ ContentResolver │ ┌───────▼──────┐ ┌───────▼───────────────┐ │ │ smsman.db │ │ Telephony provider │◄─┘ framework/ (receivers, │ (mirror) │ │ (system source-of-truth) SmsSender, WorkManager, └──────────────┘ └────────────────────────┘ notifications, role)

Data flow in one line: UI ↔ ViewModel ↔ domain interface ↔ *RepositoryImpl ↔ (Room DAO | ContentResolver), with framework/ handling everything the OS pushes at us (inbound SMS, send-status callbacks, notification actions, scheduled work).

App startup & the onboarding gate

SmsManApplication.kt · MainActivity.kt · MainViewModel.kt

  1. SmsManApplication (@HiltAndroidApp, also Configuration.Provider for WorkManager) on onCreate ensures notification channels and starts TelephonySyncCoordinator. WorkManager auto-init is disabled in the manifest so Hilt’s HiltWorkerFactory is supplied here.
  2. MainActivity installs the splash screen and keeps it on screen until MainViewModel.initialRoute becomes non-null.
  3. MainViewModel reads OnboardingTracker (DataStore) once and sets the start route to OnboardingRoute or ConversationListRoute. It also exposes settings as an eagerly-started StateFlow so the theme reacts instantly to toggles.
  4. Onboarding is a 3-step MVI flow (Welcome → Default-app role → runtime permissions). The default-app role uses RoleManager.createRequestRoleIntent(ROLE_SMS); permissions use the multiple-permissions launcher. On completion the back stack is cleared and replaced with the conversation list.
Solid pattern. Caveat: the cold deep-link path (notification tap → smsman://thread/<id>) is parsed only in onCreate; the warm path via onNewIntent is dropped (B4).

Telephony ↔ Room sync

TelephonySyncCoordinator.kt · TelephonyImporter.kt

TelephonySyncCoordinator (singleton) registers a ContentObserver on Telephony.MmsSms.CONTENT_URI, funnels change signals through a MutableSharedFlow with debounce(400ms), and calls TelephonyImporter.importRecent() — but only when the app is the default SMS app.

ContentObserver.onChange ─► changeSignal.tryEmit ─► debounce(400ms) ─► syncIfDefault() └─► importRecent() importRecent(): query newest 1000 SMS rows ─► build MessageEntity[] ─► group by threadId ─► upsert conversations (preserve pin/archive/block/mute/draft) ─► upsert messages
  • Idempotent via @Upsert; user metadata is preserved across re-imports by reading the existing row first.
  • Capped at 1000 newest rows so first launch on a huge mailbox doesn’t block.
  • Inbound SMS while default bypasses this path and writes Room directly (the observer is the safety net).
  • Upsert-only: rows deleted in Telephony by other apps are never removed from Room (B13).
  • MMS not imported (SMS table only) — the “MMS arrives in M4” comment is still true (M1).
  • Per-thread conversationDao.byId() in a loop is an N+1 query.
  • A bottom-of-file private suspend fun Flow.collect() shim exists just to terminate the chain — collect {} would do.

Receiving an SMS

SmsDeliverReceiver.kt → SmsInboundHandler.kt

SMS_DELIVER broadcast ─► SmsDeliverReceiver.onReceive getMessagesFromIntent() ─► goAsync() ─► CoroutineScope(IO).launch { inboundHandler.handle(parts, subId) } handle(): 1. concat multipart bodies; read sender, timestamp, protocol 2. if blockedNumberDao.isBlocked(normalize(sender)) → drop ◄ see B2 3. Telephony.Threads.getOrCreateThreadId(sender) (canonical thread id) 4. ContentResolver.insert into Telephony (so other apps see it) 5. upsert ConversationEntity (unreadCount+1, preserve metadata) + MessageEntity into Room 6. resolve contact, post MessagingStyle notification ◄ ignores mute (B7), history no-op (B6)

The shape is exactly right for a default SMS app: write the system store first, mirror to Room, then notify. The defects are in the details — the block check can miss (B2), the notification ignores mute (B7), and the “load unread history” line is a no-op (B6).

Sending an SMS

MessageRepositoryImpl.send() → SmsSender

  • The Telephony _id doubles as the Room PK and the PendingIntent request code — a clean way to correlate async callbacks back to the originating row.
  • Dual-SIM is handled (createForSubscriptionId on API 31+, static accessor on 30).
  • Delivery PendingIntent is omitted when the user opted out — correct.
  • Only the first recipient is used (B3).
  • The user’s “default SIM for sending” setting is never consulted (B8).
  • Multipart status uses one shared PendingIntent per part — “latest result wins,” acknowledged in comments.

Sent / delivered status (the broken link)

SmsSentStatusReceiver · SmsDeliveredStatusReceiver · MessageBubble.statusIcon

This is the most instructive bug in the codebase, so it’s worth showing how the pieces should fit vs. what happens. The send-result and delivery-report receivers update the row, and MessageBubble draws an icon from message.type + message.status:

// What's written (Android Telephony constants):
STATUS_NONE=-1   STATUS_COMPLETE=0   STATUS_PENDING=32   STATUS_FAILED=64
// What it's decoded as (app's own enum, domain/model/Message.kt):
None=-1   Sending=0   Sent=1   Delivered=2   Read=3   Failed=64
// Overlap only at -1 and 64. So COMPLETE(0) is read as "Sending", and
// Delivered(2)/Read(3) are never written by anyone → "delivered" ticks are unreachable.

The render logic is otherwise reasonable (clock for outbox/queued, error for failed, double-check for delivered/read, single check for sent) — it’s starved of correct inputs. Full write-up and fix: B1.

Notifications

MessageNotificationCoordinator · NotificationChannels · Notification*Receiver

Modern and thorough on paper: one MessagingStyle notification per thread, a published long-lived conversation shortcut (so the OS can offer Bubbles/Sharesheet), a Person with the contact photo, three actions (Reply via RemoteInput, Mark as read, Delete), a content deep-link, and a swipe-to-dismiss = mark-read intent. Request codes are bit-packed from threadId + action kind so PendingIntents don’t collide.

Scheduled send

ScheduledMessageRepositoryImpl · ScheduledSendWorker · ChatScreen.ScheduleSendDialog

Schedule a message → pre-insert a scheduled_messages row → enqueue a OneTimeWorkRequest (@HiltWorker) with an initial delay → store the work id back on the row. The worker re-loads the row by id, calls MessageRepository.send, then marks sent/failed. A pending-list screen lets you cancel (cancels the work tag + sets status Cancelled).

  • WorkManager is inexact — fine for “send around 9am,” wrong for “send at exactly 9:00.” And the app requests USE_EXACT_ALARM/SCHEDULE_EXACT_ALARM it never uses (B11, Play risk).
  • Worker returns retry() and markFailed() — contradictory; no idempotency guard (B17).
  • No future-time validation in the picker (B22).

Navigation & the MVI pattern

ui/nav/Routes.kt · AppNavHost.kt

Navigation 3: routes are plain data object/data class keys; AppNavHost holds a mutableStateListOf<Any> back stack and an entryProvider { entry<T> { … } } map. Typed args ride on the route constructor (no string paths) — pleasant and type-safe.

Every screen follows the same MVI contract:

data class XState(...)                 // single immutable state
sealed interface XIntent { ... }       // user inputs
sealed interface XEffect { ... }       // one-shot: snackbar, navigate, copy…
class XViewModel : StateFlow<XState> + SharedFlow<XEffect> + fun onIntent(XIntent)

Screens collect state with collectAsStateWithLifecycle() and run effects in a LaunchedEffect. This consistency is the single best thing about the codebase. The one architectural weakness: the back stack is in remember, not saveable, so it’s lost on process death (B16).

Database & models

data/db · domain/model

Room v1, schema exported to app/schemas/, KSP-generated Kotlin DAOs. Six tables: conversations, messages (FK→conversations, CASCADE), attachments (FK→messages, CASCADE), contacts_cache, blocked_numbers, scheduled_messages. Indices are sensibly placed (threadId/date/address/type/read; lastMessageAt etc.). Domain enums (MessageType, MessageProtocol, MmsDownloadState) carry stable raw ints that mirror Telephony contracts — a good pattern except for MessageStatus, whose raw values diverge from Telephony.Sms.STATUS_* and cause B1.

  • Mappers are pure and centralized (data/db/mapper/Mappers.kt).
  • Cache strategy in ContactsRepositoryImpl is thoughtful — negative caching, staleness window, batch resolve.
  • MessageEntity.toDomain() hard-codes attachments = emptyList(); the attachments table is never read or written (M1).
  • Destructive migration fallback still enabled (B9).

DI, theming & build

  • Hilt: DatabaseModule provides the DB + DAOs; RepositoryModule @Binds every interface to its impl; DispatchersModule exposes @IoDispatcher/@DefaultDispatcher/@MainDispatcher. @HiltWorker + a custom Configuration.Provider wire WorkManager. Textbook.
  • Theme: Material 3 with dynamic color (Android 12+), hand-built light/dark schemes, an AMOLED variant, downloadable Google Fonts (Karla/Montserrat) matching Jetchat. The SMSManTheme selection order has the AMOLED-vs-dynamic quirk (B18).
  • Build: AGP 9.2.1 / Gradle 9.4.1 / Kotlin 2.3.10, version catalog as the single source of truth, JVM 11 toolchain (daemon on 21), R8 + resource shrink on release with curated keep rules. Genuinely modern and tidy.

Clean-code analysis — strengths

  • Honest layering. The dependency arrows only point inward. You could extract domain to its own module today.
  • One pattern, repeated. MVI + injected dispatchers + flows is applied uniformly; cognitive load stays low.
  • Right platform instincts. Default-app role flow, goAsync() in receivers, Telephony-first writes, MessagingStyle + conversation shortcuts, PendingIntent request-code discipline — these are the things junior code gets wrong, and they’re right here.
  • Comments explain “why.” The non-obvious bits are documented (reverse-layout dividers, multipart caveat, dynamic-color fallback).
  • Defensive at the edges. Permission checks before contacts/SIM/notifications; runCatching around system queries; graceful empty-state fallbacks.

Clean-code analysis — weaknesses

  • Correctness debt masked by tidiness. The code reads finished, so the broken status mapping, the dead block path, and the silent recipient drop are easy to miss — exactly why they shipped.
  • No tests. Pure, testable units (ChatGrouping, RelativeTime, the status mapping, importer grouping, blocking) have zero coverage. The DI is test-friendly; the opportunity is simply unused.
  • Stubs presented as features. MMS receiver, AttachmentDao, RespondViaMessageService, the attach button, four notification channels, and Placeholders.kt are scaffolding that looks like product.
  • Two sources of truth, racing. Both receivers and the importer write message status/type; without a clear owner they can overwrite each other.
  • Docs drift. README/settings describe a different app than the code (XML vs JSON backup, “no scheduled-from-chat,” “no backup”). For a reviewer this erodes trust quickly.

Conclusion

As an engineering artifact, this is a strong, clean, modern Android codebase — the kind of structure you’d be happy to inherit. The architecture, DI, MVI and platform integration are done by someone who knows the platform. If the question is “is the code clean?”, the answer is a confident yes for structure and style.

If the question is “is this a fully-featured, production-level, Play-Store-submittable app?”, the answer is not yet. The gap isn’t cosmetic — it’s that several promises a messaging app must keep are currently broken or stubbed (status, blocking, multi-recipient, notification navigation, MMS), and there is no test safety net to keep fixes from regressing. The good news: because the bones are clean, every one of those is a contained, well-scoped fix rather than a rewrite.

Recommended path: treat the Critical/High list in the companion report as a hardening sprint, add unit tests as you fix each one (the code is built for it), resolve the two Play-policy items, then take on MMS and localization as deliberate feature work. After that, the “production” label will be earned rather than aspirational.
